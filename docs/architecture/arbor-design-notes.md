# The Outline Is the AST

**Design notes for an outliner whose files are programs.**
*Working name: **Arbor** — a placeholder handle so this document doesn't have to say "the system" four hundred times. Rename freely.*

---

## 0. How to read this

This document synthesizes a design conversation into a standalone reference. Sections 1–7 are the *why*: the conceptual commitments, argued from first principles and precedent. Sections 8–9 are the *what* and *how*: architecture and implementation notes for a macOS app backed by a Racket kernel. Section 10 lists what remains genuinely unsolved. The register is exploratory — it wanders where wandering earns its keep — but scattered through the text are statements marked **Law**. These are normative. They are the decisions an implementer must not quietly violate, because each one holds a load-bearing wall. They are collected in the appendix as a skimmable spine.

A note on names: throughout, *extension* means a thing defined by enumerating its members, and *intension* means a thing defined by a rule that generates them. A function as a list of points versus a function as an equation. This pair does more work in this document than any other distinction.

## 1. Thesis

Arbor is an outliner. Its surface syntax is Roam-flavored markdown — bullets, nesting, `[[page links]]`, `((block refs))`, `key:: value` attributes, `#tags` — extended with the better ideas from Obsidian and org-mode. A file rendered plainly is a Roam clone: outlines, transclusion, backlinks, a reference sidebar.

But the file is not rendered plainly. It is *interpreted*. The outline is parsed into a syntax tree, expanded by a macro system, evaluated where it opts into evaluation, and projected into interfaces. The outline is not a data format that a program reads; the outline **is the AST** of a program, and the app is that program's runtime.

Four moves make this more than a slogan:

First, **quotation runs in reverse**. In Lisp, code is the ambient medium and `quote` demotes an expression to data. Here prose is the ambient medium, the default denotation of every node is itself, and a marker (`=` for pure computation, `!` for effects) promotes a node to code. Documents are therefore total and inert by construction — nothing computes unless it asked to — and computation, where it appears, has the full machinery of a real language behind it: bindings, macros, phases, hygiene, modules.

Second, **rendering is projection, and attention is the evaluation strategy**. The renderer does not display the file; it displays a *resolved graph* — the file after expansion and evaluation — through projections the document itself can define. Collapsing a node is laziness. Expanding it is forcing a thunk. The user's gaze is the scheduler.

Third, **any node may be intensional**. A node's children can be enumerated by hand or generated by a rule — a query, a template instantiation, a shell command, a call to a model, a fetch from the web. Extension and intension become interconvertible: enumerate until a pattern appears, crystallize it into a rule, melt it back when you need to diverge. Abstraction becomes a gesture the medium supports, the way spreadsheets made arithmetic a gesture.

Fourth, **links carry inference**. Typed links plus rules over them give you a Datalog over your notes — derived edges, computed backlinks, consequences you did not author. And because a small agent can lazily materialize an outline behind any pointer into the world, the Datalog does not stop at the vault's edge. Your notes stop being a silo and become a theory of your domain, connected by provenance-carrying inference to everything you have read.

The rest of this document unpacks these four moves, then pins down the architecture that makes them buildable.

## 2. The Language

### 2.1 The reader

Racket's `#lang` mechanism lets a language replace the reader — the function that turns characters into syntax objects — and then supply the semantics for what those syntax objects mean. This is the same move Scribble made for documentation ("the document is a program") and Pollen made for books; Arbor makes it for the outliner. A file beginning `#lang arbor` (or, in practice, any `.md` file in an Arbor vault, with the language implied) parses not into strings but into structured syntax: each page a compilation unit, each block a form, each block's UID its identity, every node carrying source location.

The consequence is that Roam's entire feature set stops being app features and becomes language machinery:

A `((block ref))` is an **identifier reference**. A `[[page link]]` is an **import**. Transclusion is **variable lookup** — you don't copy the text, you reference the binding, so there is one value and many views of it. Backlinks are what a compiler calls **cross-references**, and they fall out of the expander for free: the binder that resolves names already knows every use site of every definition. Templates are **macros**. Queries are **expressions**. `key:: value` attributes are **typed fields**. `#tags` are **unary predicates**. The document gets, without asking, the things forty years of language engineering built: hygiene, phases, lexical scope, a module system.

One honesty note, load-bearing enough to flag early: "page as module" is a metaphor that breaks on cycles. Racket modules forbid cyclic `require`, and outline graphs are full of cycles — block refs cross pages freely in both directions. So pages do not literally compile to `module` forms importing each other. The kernel maintains its own binding store: every named block is a lazy cell, cross-page reference is lazy cell lookup, and cycle handling is a semantic decision Arbor makes explicitly (§8.4) rather than one inherited from Racket's module system. The metaphor earns its keep everywhere else — namespacing, versioned semantics via the `#lang` line, separate compilation — but the binding graph is Arbor's own.

### 2.2 Quotation, inverted

Precisely: the denotation of an authored node is the node itself. `(eval "buy milk")` = `"buy milk"`. A document containing no markers evaluates to itself in its entirety — evaluation is the identity function on pure prose, which is what makes it safe to evaluate *everything, always*. Two markers unquote:

`=` promotes a node to a **pure expression**. Its value replaces (or annotates — see residence, §3.4) the node in the resolved graph. Pure means pure: no filesystem, no network, no clock (the clock is a fact, §9.2), bounded time and memory. `=` nodes are the spreadsheet layer.

`!` promotes a node to an **effect**. `!sh sizing.sh | grep kW` runs a shell command when forced. `!fetch`, `!agent`, `!mail` — the `!` head resolves to a handler registered with the kernel, and every handler runs under an explicit capability grant (§9.2). The document, or a module it imports, can define new `!` forms; what it cannot do is mint capabilities for them.

This gives the system its shape: a vast, inert, trustworthy plain of quoted prose, punctured exactly where the author chose by wells of computation. The inversion of Lisp's default is not cosmetic. It is what lets the same medium hold your grocery list and your build system without the grocery list needing a security review.

### 2.3 Phases

The pipeline is **parse → expand → evaluate → project**, and the phase separation is doing real work:

**Parse** turns text into the concrete syntax tree — lossless, trivia-preserving (§8.2), block-granular.

**Expand** runs macros. Templates instantiate here; a "meeting note" template is a hygienic macro that receives the subtree it was invoked in as a syntax object and rewrites it. Because expansion is a phase, templates can *enforce* structure, not just emit it — and because macros are hygienic, a template's internal helper blocks cannot capture or collide with the user's names. Names a macro wants to expose must be exported explicitly (a `#:binds` declaration in the template's definition). This is also where names resolve to UIDs: `[[Heat pump retrofit]]` binds to a page identity, ambiguity becomes a rendered decoration with a quick-fix, and *renaming* becomes a refactoring — a mechanical rewrite of use sites — rather than a semantic change.

**Static semantics live at expand time.** A `schema::` page can declare that every block tagged `#person` must carry an `email::` attribute; the expander checks it before anything evaluates. Your knowledge base becomes capable of being *wrong in a detectable way*, which no current note tool offers. But — **Law: the document always renders.** A note file is not a program that fails to compile; a schema violation, a type error in an `=` block, an unresolvable reference — all of these render as decorations on the graph, never as a refusal to open the file. Failure is a decoration.

**Evaluate** forces `=` and `!` nodes on demand (§3.1) with memoization, dependency capture, and provenance stamping.

**Project** turns the resolved graph into interfaces (§3).

### 2.4 What the language layer buys, concretely

**The spreadsheet layer.** Named blocks are bindings; an `=` block referencing them transcludes their *values*. A block that sums the `cost::` attributes under a heading. A daily-note streak counter. Because references form a dependency graph, recomputation is reactive and incremental, like a build system — which is exactly what the kernel is (§9.2).

**Templates as real macros.** SmartBlocks and Obsidian templates are string expansion. Arbor templates are syntax-to-syntax transformations with the full macro toolkit: composition, abstraction over templates, inspection of the invocation site, compile-time errors ("this weekly-review template requires seven daily pages and found five").

**Contracts on knowledge.** Schemas as above; also contracts on computed blocks ("this query must return between 1 and 10 rows"), checked at eval, rendered as decorations.

**The document as image.** Transcluding a code block elsewhere shares a binding, so refactoring notes is refactoring code. Over time the vault becomes a personal computing environment in the Smalltalk-image sense: your todo system, your trackers, your small tools live *in* the outline, as outline — inspectable, refactorable, versioned with the prose they serve — rather than in plugins beside it.

An illustrative sketch (surface syntax deliberately not final):

```
- Project:: Heat pump retrofit  ^hp1
	- Quotes
		- Vendor A — cost:: 4200
		- Vendor B — cost:: 1150
	- = (sum (attr-under 'cost ^hp1))
	- !sh sizing.sh --area 140 | grep kW
	- {{view: table (query (and #todo (under ^hp1)))}}
```

The first two children are quoted prose with typed fields. The `=` block is a live sum. The `!sh` block runs when expanded, under a capability grant, and its output becomes a child node whose residence (transient, cached, or written back) is declared policy, not accident. The `{{view}}` block is a projection — the next section's subject.

## 3. The Renderer

### 3.1 Attention-driven evaluation

Take the pipeline seriously and the renderer becomes a compiler with an unusual scheduler: *attention drives evaluation*. Expanding a node forces a thunk; collapse is not hiding, it is laziness. This is a genuinely new answer to the question "when does a document compute?" — not on load (the web's answer), not on explicit run (the notebook's answer), but **on inspection**. The protocol makes this literal: the renderer subscribes to a region of the resolved graph — a root, a projection, a depth — and *subscribing is forcing* (§9.1). Background subscriptions exist too (an agenda view, a scheduled recompute, the agent's standing queries), which is one of the reasons the kernel is a daemon and not a library inside the renderer.

Attention also drives the cache. Memoization makes forcing cheap on revisit; eviction favors what hasn't been looked at. The gaze is both the scheduler and the garbage collector's hint.

### 3.2 Nouns, verbs, and the sanctity of gesture

The renderer exposes a small vocabulary. Nouns: block, span, badge, table, board, calendar, embed, decoration. Verbs: expand, collapse, follow, edit, toggle, drag, force, pin. Documents compose these — a `{{view: kanban ...}}` block, an org-style `[3/7]` completion cookie on a todo list, a toggle cycling a `todo::` attribute through declared states — and can define new projections as pure functions (ring 0, §9.2) from the resolved graph to widget trees.

Two disciplines keep this power from eating itself:

**Law: the trusted chrome is not programmable by documents.** A document that programs its renderer can lie about itself. The frame — what file this is, what capabilities are live, what is derived versus authored, the audit trail — is rendered by the app from kernel truth, and no document-defined projection can draw over it. Documents program the renderer only through the kernel's vetted vocabulary.

**Law: uniform gestures are sacred.** Expand, follow, and edit mean the same thing in every projection, however bespoke. Infinite malleability re-imports the "every app is different" problem into your own notes; if a kanban card doesn't expand the way a bullet does, legibility dies. Custom views customize *what* is shown, never *how the hand works*.

### 3.3 Views are lenses

Every projection is a bidirectional lens in the Foster–Pierce sense, because every view must be *editable* and edits must land in source. There are two lenses, composed:

The **compile-lens**: source (lossless concrete syntax tree) ↔ resolved graph. Its Get is the compiler — parse, expand, evaluate. Its Put is a refactoring engine.

The **view-lens**: resolved graph ↔ widgets. Its Get is the projection function; its Put translates a gesture (drag this kanban card, toggle this checkbox, edit this table cell) into an edit on the resolved graph, which the compile-lens then routes to source.

Routing goes **by provenance**. Every node in the resolved graph is stamped with where it came from: an authored node carries its source location and UID, so editing it is a surgical text edit; a computed node carries the rule instance and input hashes that produced it. Editing a computed node consults its generator's declared update policy — the database view-update problem, and many cases are trivially updatable (the kanban card *is* a source block, relocated by the projection, so dragging it is a `move` on source; the todo toggle is an attribute write). When no update policy exists, the edit **materializes as an override**: a stored fact, keyed to the provenance path, that shadows the computed value. **Law: the override is the universal fallback Put.** It makes every view editable at the price of *visible divergence* — the residue renders as residue, a badge on the node saying "this diverges from its rule."

Be honest about the lens laws. GetPut holds: render and touch nothing, and nothing changes. PutGet holds only up to canonicalization and only where an update policy exists; elsewhere, violated laws produce residue instead of corruption. That is the correct trade. First, do no harm; second, never silently discard an edit; third, make every divergence visible.

### 3.4 Residence, and the mark of the derived

When an effect or evaluation produces content, where does the value live? Org-babel already named the options — `:results silent`, `replace`, `append` — and Arbor adopts the question as declared policy per form: **transient** (exists only in the view phase; the `!sh` output you glance at and collapse), **cached** (persisted derived state, replayable, evictable), or **written back** (materialized into the source file).

Write-back is self-modifying code, which the Lisp tradition is comfortable with — that's what an image is — but it demands a covenant. **Law: derived text is always distinguishable from authored text.** A written-back node carries an indelible provenance mark (concretely: a `derived:: rule@inputhash` attribute survives serialization to plain markdown, §9.3), so staleness is detectable even by grep, and no future reader — human or kernel — can mistake the machine's words for yours. The moment authored and computed content become indistinguishable, the document stops being trustworthy as a record of what you actually said, and the whole edifice tips over.

### 3.5 Where this leads

Views as document-defined projections is where Arbor stops being a Roam clone and becomes a platform. A subtree rendered as outline, table, kanban, calendar, timeline; a transient cross-vault agenda you can *act through* (org-mode's agenda is the existence proof that this pattern carries an entire workflow); eventually, "app" and "document" cease to be different kinds of thing. The lineage runs through Boxer, HyperCard, and above all Engelbart's NLS — which was literally an outline processor with computed views. Arbor is, in one framing, NLS completed with a macro system.

## 4. Intension

### 4.1 Enumeration versus computation

A pure-data outline is extensional: it can only enumerate. Arbor lets any node be intensional: defined by a rule that generates its extension. A function as a list of points versus a function as an equation. This single move has consequences all the way down; this section walks them.

### 4.2 Hierarchy stops being a commitment

The oldest complaint in filing — Vannevar Bush's, in 1945 — is that a tree forces one taxonomy. This note goes under *Project X* or under *Alice*: pick one, and pay forever. If children can be computed, then by-project, by-person, by-time are just different groupings of the same underlying facts, and the tree on screen is a projection chosen per purpose. Nesting becomes presentation, not storage. "Where do I file this" dissolves, because the answer is "everywhere a query puts it." The outline keeps its virtue — nesting as levels of in-concept detail, the shape thought actually has — while shedding its historic cost.

### 4.3 Abstraction becomes a gesture

Select five structurally similar subtrees. Extract the pattern. They become instances of a parameterized template, their differences now arguments. This is "extract function" — the refactoring IDEs have had for decades and no note tool ever has — performed on thought.

Real knowledge never fully compresses, so the mechanism is **rule plus residual**: an instance transcludes its template and carries local overrides. This is prototype inheritance à la Self; it is also the spreadsheet's "overwrite the formula in this one cell." Change the rule and every instance updates, while overrides persist — or surface as visible conflicts to resolve. That is schema evolution for your own concepts, and the override machinery of §3.3 is the same machinery: divergence, stored and displayed.

Both directions stay open, and must stay cheap. **Enumerate until a pattern emerges; crystallize into a rule; melt back into data when you need to diverge.** Freezing and melting. Premature abstraction is as deadly in notes as in code, so de-abstraction — "inline this template here, I'm going off-script" — is a first-class gesture, not an apology.

The inference direction matters too: given examples, *propose* the rule. This is programming-by-example — FlashFill territory — and a small language model slots in cleanly as one possible generalizer among several (§5.2 takes this further). The tool's stance: abstraction is offered, never imposed.

### 4.4 Structure without rigidity

Note what the mechanism does *not* mandate: structure. Rule-plus-residual doesn't require the abstraction to be a tree, a table, or an object — the rigid shapes Roam, Notion, and Airtable force you to choose between. The generating entity behind an intensional node can be a template, yes; but also a plain program, an external function (replace a set of enumerated facts with a reference to *the thing that generates them* — a Wikipedia article, a search, an API — the Kolmogorov–Chaitin move of storing the program instead of its output); or a *model*. Free-form text has hidden structure — a poem has meter, rhyme, syntax, an image-graph — and a BERT-class model can serve as the generator that recovers it. Section 6 develops this: the structured/unstructured dichotomy was never a property of the text, only of a reading.

### 4.5 Links become inference

If nesting is intra-concept detail and links are inter-concept relation, then rules over typed links give you a **Datalog over your notes**. Ground facts fall out of the parse — `parent(a,b)`, `attr(b,'cost',4200)`, `link(b,c,'blocks')`, `tag(b,'todo')` — and rules derive edges you never wrote:

```
under(A,C)        :- parent(A,C).
under(A,C)        :- parent(A,B), under(B,C).
blocked(T)        :- link(T,D,'blocks'), open(D).
transitively-blocked(T) :- blocked(T).
transitively-blocked(T) :- link(T,D,'blocks'), transitively-blocked(D).
```

The backlinks panel grows a second column: not just what *mentions* this, but what *follows from* it. The delicious irony: Roam already runs on Datascript — a Datalog — and hides it as an implementation detail. Arbor promotes the engine to user-level semantics.

### 4.6 The epistemic consequence

Chaitin's slogan — comprehension is compression — means the act of refactoring enumerations into rules *is* the act of understanding, and Arbor makes that act first-class. An extensional note can only tell you what you told it. An intensional note can tell you something you didn't know you knew: computation produces consequences you didn't author, and when a derived view looks wrong, either your data or your rule is wrong. **Your notes become falsifiable.** That is the line where a medium stops storing knowledge and starts generating it. The end state is that "my notes" converge on "my theory of my domain"; the renderer is the observatory pointed at it; editing becomes theory revision.

Spreadsheets gave a hundred million people programming over numbers by hiding the program inside a familiar grid — the only end-user programming model that ever won. Arbor is the same trick played on symbolic structure: programming over concepts, hidden inside an outline.

## 5. The World as Outline

### 5.1 The agent and the shadow outline

Consider a small, fast agent with web access whose only job is to produce outlines. Any phrase in any note can be linked outward, and behind the link the agent lazily materializes a **shadow outline** of the target: a page, a paper, a dataset, a person, rendered in Arbor's own structure — expandable, queryable, linkable — as the web's contribution to your graph. The vault's Datalog then extends past the filesystem: `cites(paper, paper)`, `contradicts(claim, claim)`, `instance-of(entity, class)` over facts you never typed. Your notes stop being a silo and participate in the whole of recorded knowledge, mediated by a robot that organizes it.

This idea has famous graves, and it is worth knowing why the graves are empty of Arbor's corpse. Xanadu's docuverse required the world to adopt Nelson's format. The Semantic Web required authors to annotate their own pages; nobody did. Both died of the cooperation problem. The agent sidesteps it: it supplies **at read time** the semantics authors refused to supply at write time. Nobody has to cooperate; the model retrofits outline structure onto arbitrary sources, leaning on Wikidata and its kin as the already-structured backbone where they exist. Web clippers copy extensions; Arbor links intensions — the pointer plus its generating function, the web as your outline's lazily materialized tail.

### 5.2 Pinning: the impure generator

The shadow generator is impure. Its inputs include model weights, the live web, and the clock; the same intension yields different extensions on different days. Two obligations follow.

**Law: shadow outlines are pinned.** Every materialization is an **observation**: a content-addressed, timestamped snapshot recording the source, the tool and tool-version that extracted it, and the extraction itself. Facts derived from the world reference the observation's hash, never "the web." Re-derivation is an explicit, dated act — and because it is, *the diff between two derivations is a first-class, computable view*: "what changed since I last looked" becomes a query. Nix faced exactly this shape of problem and answered the same way: fixed-output derivations — impure fetch, declared result.

**Law: provenance flows through inference.** Once Datalog derives conclusions from foreign premises, every derived fact must carry its justification — the rule and the facts it consumed, transitively down to authored statements and pinned observations. This is the truth-maintenance tradition (Doyle's TMS, de Kleer's ATMS): distrust a source and its consequences retract, visibly. The backlinks panel grows an **epistemics tab**: for any node, not "what links here" but *what believes this, and on whose word* — a justification tree whose leaves are either "you wrote this," "this rule derived it from these inputs," or "this tool observed it at this URL on this date." Marking a source unreliable renders as: "17 conclusions lost support."

### 5.3 The autonomy dial

The agent can materialize on demand (safe default), maintain standing shadow outlines for pinned entities (a watched competitor, a followed literature), or propose new links and facts into your authored notes. The last crosses a line and is governed by §3.4's covenant — agent contributions are derived content, marked as such, and land as *suggestions* (residue awaiting adoption) unless a capability explicitly grants write-back. The dial's setting is per-vault, per-source policy, stored as facts, visible in chrome.

## 6. Text With Hidden Structure

### 6.1 Parsing as reading

The structured-versus-unstructured dichotomy dissolves under one observation: structure was never a property of the text; it is a property of a *reading*. A poem is one string under five parses — meter, rhyme scheme, syntax, image-graph, allusion. A parser is just a Get. With a BERT-class soft parser in the loop, *every* text is already in the system; the outline is merely the text whose parse is trivial and whose Put is easy. This is schema-on-read where the schema is itself a note: a `reading::` page declares what to look for, the parser materializes the reading as an intensional overlay, and different readings of the same text coexist without conflict, because none of them is the text.

### 6.2 Soft edges and their suspects

Model-produced structure makes the Datalog probabilistic whether you invited that or not. Confidence must propagate through inference (the semiring machinery of §9.2 makes this one parameter, not a rewrite), and — a UI obligation as much as an engine one — must not be painted over: a derived row resting on a 0.6-confidence parse renders differently from one resting on your own words. When a derived view looks wrong there are now three suspects, not two: the data, the rule, or the parse.

### 6.3 Annotation is supervision

Overriding a parse is annotation, and annotation is the same mechanism as every other override in the system: a stored fact, keyed to provenance, that shadows the generated value — rule-plus-residual again, except now the residual is *supervision*. Your corrections accumulate into constraints on future readings: the model's leash, braided from your own disagreements, versioned with your notes, yours to inspect. (Whether the leash merely constrains outputs or eventually fine-tunes a local model is an implementation dial, not a design question; the design question — where corrections live and who owns them — is answered: in the vault, as facts, by you.)

## 7. The Library

### 7.1 The reference machine

Kolmogorov complexity is relative to a reference machine, and the invariance theorem's "up to an additive constant" hides that the constant is your entire quality of life. The library **is** the reference machine. Every generator added — a date algebra, a citation resolver, a habit-tracker vocabulary, a better reading for tables — retroactively compresses and enriches every note that can now call it: a browser upgrade improving pages written years ago. As the library improves, the notes improve. This is the Mathematica lesson, and it is worth stating what the lesson actually is: less the six thousand functions than the **dictatorial curation**. Uniform conventions — one naming scheme, one calling style, one documentation shape — are *why* Mathematica's functions compose. npm is the counterexample: enormous, and mutually indifferent. Arbor's standard library is curated like a language, not accreted like a package registry; third-party vocabularies exist, but the core grows slowly and coherently.

A library entry, ideally, is a triple: a **recognizer** (how this vocabulary appears in surface syntax — its parse), a **semantics** (what it computes), and a **printer/projection** (how it renders and serializes). Languages-as-libraries, Racket's own story, applied at the vocabulary scale.

### 7.2 Versioned meaning

The dark side of a living library is that upgrades change meaning. Racket has already paid this bill, and Arbor inherits the receipt: **Law: the `#lang` line pins semantics.** A file declaring `#lang arbor/2026.08` means the same thing forever; old notes keep their old meanings; migration is an explicit refactoring (with tooling — the compile-lens's Put, again) rather than silent drift. A vault may set a default version; a file may override it; the kernel ships every version it has ever shipped. Notes are documents of record. Records do not change meaning when the software updates.

## 8. Architecture: Where Authority Pins

Three questions decide the system's shape, and they turn out to be one question — *where does each kind of authority pin?* — answered layer by layer. Authorship pins in the text. Identity pins in the syntax tree and its CRDT. Meaning pins in the resolved graph, under a versioned semantics. Attention pins in the projection. Get the pinning right and the rest is engineering.

### 8.1 Who owns the computation

Split "owns" into three authorities.

**Meaning is owned by the document.** The `#lang` line plus the pinned library version make the file self-describing: any conforming engine must agree on what it denotes. Put semantics anywhere else — in a service, in the app version, in a server-side interpreter — and your notes' meaning is hostage to that service's uptime and roadmap. The file is law.

**Execution is owned by the kernel**: the Racket engine hosted in a long-running, memoizing, incremental daemon — Roslyn/rust-analyzer in shape, Jupyter/Mathematica in topology (Mathematica has been frontend/kernel since 1988; the split is older than most of its users). It must be a daemon and not a library inside the renderer for three reasons. Simultaneous projections need one resolved graph shared by many views. Background work — the agent, standing queries, scheduled recomputes — runs with no window open. And effects need one accountable boundary: `!` forms execute in the kernel under capability grants with an audit log, and documents program the renderer only through the kernel's vetted vocabulary, which is what keeps the trusted chrome trustworthy. The kernel is the executive.

**Presentation owns nothing.** The renderer holds no state that matters: it is a subscriber, a projector of kernel truth, and the fastest possible echo of in-flight typing (§9.4). The renderer is the press.

The rejected option deserves its epitaph: computation in the storage/sync layer, Firebase-style, where meaning lives in nobody's file and every open is a negotiation with a server. Third parties may still *execute* — heavy jobs, the web agent, a rented GPU — but their outputs re-enter only as pinned observations. The cloud can compute for you without owning you.

### 8.2 What the lens operates on

At the bottom sits the file — held in memory as a **lossless concrete syntax tree**: Roslyn-style green/red trees, trivia preserved (every space, every marker character), so that the compile-lens's Put is a surgical text edit that never reformats your prose. Racket syntax objects do not preserve trivia, so the kernel owns the green tree and *derives* syntax objects from it — srcloc and lexical scopes attached — for expansion. The green tree is C, the source of the outer lens.

The renderer never reads C. It reads A: the **resolved graph**, post-expansion, post-evaluation, every node stamped with provenance — source UID for authored nodes; rule instance and input hashes for computed ones. Two lenses compose: compile-lens (C ↔ A) and view-lens (A ↔ widgets); §3.3 gave their Put discipline — route by provenance, honor declared update policies, fall back to visible overrides.

One elegance worth naming: **rename is a Put**. Changing a page's title is an edit on A that the compile-lens translates into a rewrite of every use site in C — the refactoring engine and the editing model are the same machinery.

### 8.3 What syncs

Datalog's own vocabulary answers this: the **extensional database syncs; the intensional database derives**. Replicate anything that is not a deterministic function of other replicated state; recompute everything else locally. Never sync the resolved graph.

The EDB is three CRDTs, braided:

A **block tree** whose node identity is the UID, with an explicit *move* operation — because concurrent reparenting is *the* outliner conflict, and naive tree merges duplicate nodes or create cycles; Kleppmann et al.'s move-operation work is the correction, and choosing a CRDT library that implements it is a hard requirement (§9.3).

A **per-block text CRDT** with stable span anchors, Peritext-shaped, so inline references and marks survive concurrent edits.

**Attribute maps**, last-writer-wins per key.

**Law: identity lives in the sync layer.** UIDs are what make `((refs))` merge-stable; mint them at block creation, in the CRDT, not above it. And legislate the classic ambiguity now rather than in a migration: **Law (block split): the head keeps the UID.** When a block splits, the half containing the original first grapheme retains the identity; the tail gets a fresh UID; span-anchored references soften the cases where the referenced content moved to the tail, and an explicit "identity follows selection" gesture exists for when the user knows better.

Observations — agent snapshots, `!` write-backs, anything fetched or measured — are *not* recomputable, so they sync too, as content-addressed blobs referenced from CRDT facts. The real dividing line is not human-versus-machine but **deterministic-versus-observed**.

Which yields the system's conservation law, and its best test: **Law (convergence): identical (source, observations, `#lang` version) ⇒ identical resolved graphs.** Two kernels that have synced must agree on everything derived, bit for bit. This is simultaneously the correctness criterion for sync, the reproducibility criterion for the kernel, and a property test the CI runs forever (§9.7).

### 8.4 Legislated semantics

Small decisions that must be made once, globally, and early — collected here so no implementer rediscovers them mid-crisis:

**Cycles at the value level are errors, rendered as decorations** showing the cycle path — the spreadsheet's circular-reference discipline. An opt-in `#:fix` annotation may later allow bounded-iteration fixpoints with an explicit convergence test, for the brave; it is not v1. (Cycles at the *reference* level — block A links block B links block A — are of course fine; laziness handles inspection, and only value-dependency cycles are ill-founded.)

**The clock is a fact.** `(today)` reads a kernel-maintained date fact; time-dependent notes recompute when the day-fact changes, which makes temporal recomputation *explainable* — the daily note didn't mysteriously change, its input did. Time is an observation like any other.

**Stratified negation** in the Datalog; no negation through recursion. Boring, correct, done.

**Effect idempotency:** write-backs carry an idempotency key `(rule, input-hash)`, so a re-run — or a concurrent run on another replica — deduplicates instead of duplicating output blocks after merge.

## 9. Implementation Notes: macOS App + Racket Kernel

What follows is opinionated. Where my information may have aged (library versions, binding maturity), I say so; verify at implementation time. The load-bearing choices are marked as Laws like everything else.

### 9.1 Topology and protocol

**Two processes, plus helpers.** The app (Swift) and the kernel (Racket) run as separate processes. The kernel is spawned as a child of the app for lifecycle simplicity, but *designed daemon-shaped* — no assumption that a window exists — so background scheduling can later move it to a LaunchAgent without surgery. The agent (§9.5) is a third process with its own entitlements. Separate processes buy crash isolation, independent memory ceilings, and honest interfaces; **Law: the editor survives the kernel.** If the kernel dies, the renderer keeps editing (the text substrate is local, see below), decorations go stale with a subtle indicator, and a kernel restart resyncs. A notes app that beachballs because an interpreter crashed has failed its one job.

**Transport: a Unix domain socket carrying JSON-RPC 2.0 with LSP-style `Content-Length` framing.** Not XPC — Racket speaks sockets natively (`unix-socket-lib`), UDS is debuggable with `nc` and portable to a future Linux kernel host, and the LSP framing means existing tooling and reflexes apply. JSON first; switch hot paths to CBOR only when profiling demands it. Version handshake at connect; the kernel serves multiple clients (app windows, CLI, agent) concurrently.

**The protocol embodies the thesis.** Its core is subscription, and *subscribing is forcing*:

```
→ {"id":7,"method":"view/subscribe",
   "params":{"root":"hp1","projection":"outline","depth":2,"semiring":"why"}}
← {"method":"view/patch","params":{"sub":7,"ops":[
     {"at":"hp1/2","node":{"kind":"value","text":"5350",
      "provenance":{"rule":"sum@ab12","inputs":["c4f9","77e0"]}}} ]}}
→ {"id":8,"method":"intent/apply",
   "params":{"provenance":"hp1/3","put":{"kind":"toggle","attr":"todo","to":"DONE"}}}
→ {"id":9,"method":"eval/force","params":{"node":"hp1/4"}}   // expand the !sh block
```

Method families: `doc/*` (open, close, external-change), `sync/*` (CRDT message channel — the app and kernel synchronize their replicas over the same protocol any two network peers would use, which means local IPC dogfoods the sync system daily), `view/*` (subscribe, unsubscribe, patch pushes), `intent/*` (puts, routed by provenance), `eval/*` (force, invalidate), `cap/*` (grant, revoke, query), `obs/*` (put observation, get by hash). Subscriptions carry a semiring parameter so the epistemics tab is just the same view subscribed under `why` (§9.2).

### 9.2 The kernel

A Racket application, structured as eight modules. In dependency order:

**Reader.** A custom parser — do not fight readtables; outline grammar is line-and-indent shaped, not sexp-shaped — producing the green tree. Expose a real `#lang arbor` via `syntax/module-reader` as well, so files are loadable by `raco` for CLI and batch use (`arbor render page.md`, headless, for CI and the agent). Prior art for indentation-sensitive readers in the Racket world: Rhombus's shrubbery notation. The crucial structural gift: **blocks are parse islands.** A block is line-delimited; an edit inside a block reparses that block alone; block boundaries are stable parse boundaries. The outline is not just the AST — it is the *incremental compilation unit*, which is why Arbor needs no tree-sitter-style general incremental parsing. This is a genuine architectural advantage of the outline form and half the reason the kernel can feel instant.

**Green tree store.** Lossless CST per §8.2: green nodes (identity-free, shareable, trivia-carrying), red overlay (parents, positions, UIDs). Syntax objects are derived views for the expander, srcloc pointing back into the green tree.

**Binder.** Names → UIDs, built at expand; scope sets for hygiene; the rename-as-Put refactoring; ambiguity decorations with quick-fixes; alias facts.

**Expander.** The macro protocol over outline syntax objects. Templates receive their invocation subtree; hygiene via scopes; explicit `#:binds` exports; schema/contract checking; all failures emitted as decorations (**the document always renders**).

**Build core.** The kernel *is* a build system, and "Build Systems à la Carte" (Mokhov, Mitchell, Peyton Jones) is the map: choose a **suspending scheduler with verifying traces** — the Salsa/Shake quadrant. Memo tables keyed by `(node, phase, semiring)`; dynamic dependency capture via a parameter the evaluator swells as it reads inputs; invalidation by trace verification on the dirtied set. v1 recomputes from source on open; persisted traces (in `.arbor/cache.sqlite`) are an optimization to add when cold-open profiling says so, not before.

**Evaluator.** Ring 0 execution of `=` forms inside `racket/sandbox`: memory and time limits, no filesystem, no network, no ambient clock (the day-fact is an input), deterministic seeds. The security model is three rings, and it is Arbor's, not the OS's:

*Ring 0 — pure.* Default for all `=` forms, projections, queries. Total, deterministic, effect-free. No grant needed; this is why documents are safe to evaluate on inspection.

*Ring 1 — vault effects.* Filesystem reads within the vault, `!sh` with a per-command grant, write-backs. Requires an explicit capability, granted per document or per rule, stored as facts, surfaced in chrome.

*Ring 2 — world.* Network. Lives only in the agent process; the kernel itself carries no network entitlement, which turns a policy into a mechanism.

Every ring 1–2 execution appends to the **audit log — which is itself an Arbor page**: an outline of effect records, queryable like anything else. The system keeps its books in its own medium.

**Datalog engine.** Write your own semi-naive evaluator — roughly five hundred lines — rather than adopting the stock `datalog` collection, because you need two things it will not give you: delta evaluation for incrementality, and **semiring parameterization** for provenance. The Green–Karvounarakis–Tannen insight collapses three features into one evaluator: run it over the boolean semiring and you have ordinary truth; over the why-provenance semiring and every fact carries its justification tree (the epistemics tab, TMS-style retraction); over a Viterbi semiring (`⊗ = min` or product, `⊕ = max`) and confidence propagates through inference (§6.2). One engine, one parameter, three epistemologies. Stratified negation; EDB in memory, rebuilt from the CRDT at open — a 100k-block vault is small by database standards, and one source of truth beats a cache hierarchy until profiling proves otherwise.

**Effect broker and protocol server.** Capability table, `!` handler registry, idempotency keys, audit writer; the JSON-RPC server over `unix-socket-lib`.

Two Racket-specific cautions. First, pages are not literal `module` forms (§2.1): the kernel's binding store is lazy cells with cycle detection, and cross-page reference never touches `require`. Second — this one bites at the finish line — **Racket CS generates machine code at runtime.** Under macOS's hardened runtime the embedded kernel will need the `com.apple.security.cs.allow-jit` entitlement (and MAP_JIT-aware allocation; possibly `allow-unsigned-executable-memory` depending on Racket version). Build and notarize a skeletal kernel in week one, not month six; §9.7 makes this a standing CI job.

### 9.3 Storage and sync

**The vault is a directory of plain markdown files.** This is non-negotiable culture, not just engineering: greppable, git-able, outliving the app. But CRDTs want op logs, so the resolution is a two-layer truth: the CRDT binary log (in `.arbor/`) is the *operational* truth that sync and identity run on, and the kernel **continuously materializes** the markdown files from it. Materialization is deterministic because CRDT state is convergent — same replicas, same bytes — so files diff cleanly in git across machines. Alongside: `.arbor/cas/` for content-addressed observations, `.arbor/index.sqlite` for full-text and vector indexes. **Law: never lose user bytes.** An external edit the importer cannot parse is quarantined as a raw-text block, marked, rendered; it is never dropped or "fixed."

**External edits** (the user opens a file in Vim; FSEvents fires): parse the new file, tree-diff against the materialized state — UID anchors pin the unambiguous matches, similarity matching (Myers over block sequences) resolves the rest — and import the delta as synthetic CRDT ops. This is the hairiest code path in the system; budget for it accordingly, and let the deterministic materializer keep it rare by making the on-disk files pleasant enough that external edits are casual, not corrective.

**Visible UIDs are lazy.** Every block has an internal CRDT identity from birth; a *visible* anchor (trailing `^uid`, Obsidian-style) is materialized into the text only when something references the block, so files stay clean. Obsidian proved the ergonomics of exactly this trick.

**CRDT library.** The braid needs a movable tree (Kleppmann move semantics), rich-text with stable span anchors (Peritext lineage), and maps. As of this writing the two candidates are **Loro** (Rust core; implements the move operation and Peritext-inspired rich text — the closest shape-match to the braid; Swift bindings exist, Racket reaches the core via a thin C shim over its FFI) and **Automerge** (larger ecosystem; maintained C and Swift bindings; verify movable-tree status in the current major version). Evaluate both against the braid's three requirements plus undo support (Loro ships an UndoManager; concurrent-safe undo is a known dragon — prefer the library's implementation to your own). Whichever wins, both processes link the same Rust core: Swift bindings in the app, `ffi/unsafe` over the C ABI in the kernel, replicas synchronized over the `sync/*` channel. The sync *server*, when you build one, is a dumb relay — the CRDT makes it so — and end-to-end encryption falls out of the server's dumbness.

### 9.4 The app

**Native, AppKit shell, TextKit 2 outline surface, SwiftUI chrome.** The honest fork in the road: many winning tools in this space are web-views (Obsidian, Notion), and a WKWebView + ProseMirror surface would de-risk the editor enormously. The protocol is deliberately UI-agnostic so that escape hatch stays open forever. But the thesis — bespoke projections with uniform gestures, embedded live widgets, platform-grade text feel — is exactly the territory where the web stack fights you and TextKit 2 was built for you: `NSTextLayoutManager` with custom `NSTextLayoutFragment` subclasses gives each block its own layout object, which is precisely what block-granular rendering, folding, and widget embedding want. Bear and Craft are existence proofs that native editors of this ambition ship. Recommendation: native, with the web fallback as insurance you never cash.

Concretely: each block is a text element; computed widgets (tables, boards, badges, completion cookies) are attachment view providers hosting SwiftUI or AppKit views inline; folding hides text elements; the sidebars (organization, references, epistemics) are SwiftUI panes fed by their own subscriptions. Projections that aren't text-shaped at all — the kanban board, the calendar — are collection views whose cells carry provenance and whose gestures compile to `intent/apply`.

**The keystroke path is the whole game.** **Law: typing never waits on the kernel.** The renderer holds a live CRDT replica in-process; a keystroke mutates the block's text CRDT locally and paints in the same frame. Change events stream to the kernel over `sync/*`; the kernel folds them into the green tree, reparses the one dirty block, verifies traces outward through the dependency graph, and pushes decoration and value patches back *asynchronously*. This is the LSP division of labor, adopted with both hands: the renderer is authoritative for in-flight text at frame rate; the kernel is authoritative for meaning; the CRDT is authoritative for source, and since both processes hold replicas of the same document, "local echo" is not a consistency hack — it is just... the CRDT, doing its one job. Undo is intent-level, backed by the CRDT library's undo manager; selections and cursors are `(block-uid, span-anchor)` pairs, which is also what collaborative presence will want later.

Latency budgets, treated as regressions when violated: keystroke-to-glyph under 16ms wholly renderer-side; edit-to-decoration p50 under 50ms on a 10k-block vault; force-of-a-collapsed-pure-node under 100ms; cold open under 1s per 10k blocks; steady-state memory for app+kernel under ~500MB on a typical vault.

### 9.5 The agent and local models

The agent is a separate process — the only one with a network entitlement — speaking the same protocol as any other kernel client. It executes ring-2 work the kernel schedules: materializing shadow outlines, refreshing standing observations, running `!fetch`. Everything it produces enters the system as content-addressed observations via `obs/put`; it has no other write path. Suggested-edit mode (§5.3) lands its proposals as residue, never as silent authored text.

Local models, in escalation order: **v0**, Apple's NaturalLanguage framework — `NLTagger` for entity recognition, `NLEmbedding` for similarity — which is free, on-device, and enough to make link-suggestion and soft parsing real. **v1**, a small local model via llama.cpp or MLX for schema-directed extraction (constrained decoding straight into fact shapes: the model literally cannot emit anything but valid EDB rows) and for the programming-by-example generalizer of §4.3. Hosted frontier models are a capability-gated option for the shadow-outline generator, behind the same observation discipline — the pin doesn't care how smart the observer was. Embedding index in `index.sqlite` via a vector extension (sqlite-vec, as of this writing) or usearch; embeddings are derived state, rebuilt on demand, never synced.

### 9.6 Packaging and distribution

Bundle the kernel with `raco exe` + `raco distribute` into `Contents/Resources/kernel/`; sign every dylib in the bundle; hardened runtime with the JIT entitlement per §9.2; notarize. **Distribute directly (Sparkle for updates), not through the Mac App Store** — `!sh` and user-authored effects sit somewhere between awkward and impossible under App Review, and the audience for this tool expects direct distribution anyway. The OS-level App Sandbox is optional and secondary; Arbor's real security model is the ring system, which sandboxes *document code* regardless of what the OS thinks of the app. If you do adopt the App Sandbox, vault access flows through security-scoped bookmarks. A CLI (`arbor render`, `arbor query`, `arbor fsck`) ships in the bundle and symlinks into PATH; it is the same kernel, headless, and it is how CI, scripts, and skeptics verify that the files really do mean what the app says they mean.

### 9.7 Milestones, tests, and the order of battle

Each milestone is independently useful — the system should be someone's daily notes app from M1 onward, because a substrate this ambitious survives only by being a good outliner every single day while the ambition compounds.

**M0 — the file speaks.** Reader, green tree, materializer; `arbor render` produces HTML; round-trip property (`print ∘ parse = id` on bytes) holds. Exit: a vault renders read-only in a bare window.

**M1 — the loop closes.** CRDT braid in both processes, keystroke path, outline projection with fold/expand, external-edit import. Exit: it is a good outliner; a week of real notes lives in it.

**M2 — the spreadsheet layer.** `=` forms, ring 0 sandbox, build core with trace verification, value decorations, residence policies. Exit: the cost-sum example works and stays correct under editing.

**M3 — inference.** Datalog engine (boolean + why semirings), structure facts, queries as blocks, backlinks and derived-edge panel, justification view. Exit: the epistemics tab answers "why is this here" for every derived node.

**M4 — abstraction.** Macro protocol, templates with hygiene and `#:binds`, schemas and contract decorations, rename-as-refactoring, extract-template gesture with rule-plus-residual overrides. Exit: five similar subtrees become one template and five diffs, and melt back.

**M5 — projections.** View-lens framework, table and kanban with Put-by-provenance, override residue rendering, uniform-gesture conformance tests. Exit: drag a kanban card, watch the source file change surgically.

**M6 — the world.** `!` forms, capability system, audit page, agent process, observations CAS, shadow outlines with pinning and re-derivation diffs, confidence semiring. Exit: a phrase in a note expands into a pinned outline of a webpage, and distrusting the source visibly retracts its consequences.

**M7 — sync.** Relay server, second device, convergence property in CI (two replicas, random op interleavings, byte-identical materialization and resolved graphs). Exit: the Law of Convergence holds under a fuzzer that runs forever.

Standing test posture from day one: property tests (rackcheck) for lens laws — GetPut always, PutGet-up-to-canonicalization where policies exist, residue-not-corruption elsewhere; CRDT convergence fuzzing; golden files for the materializer; semiring engine cross-checks (why-provenance leaves must reproduce boolean results when flattened); and a CI job that signs, notarizes, and launches a skeletal build so the JIT entitlement and every future macOS security change bites a robot instead of a release.

## 10. Open Problems

Honest gaps, in rough order of how much they scare me.

**Justification trees for humans.** The epistemics tab is easy to build and hard to make readable. Provenance graphs explode; the UI problem — summarizing *why* without lying — is unsolved everywhere it has been attempted. Arbor needs it solved at least for the common shapes (one rule, few inputs) and gracefully degraded elsewhere.

**Override sprawl.** Rule-plus-residual is the right semantics and a potential hoarding disorder: a vault silted with hundreds of forgotten divergences. Needed: residue dashboards, "reabsorb this override into the rule" refactorings, and staleness pressure (residue whose rule has since changed should itch).

**Probabilistic honesty.** Confidence propagation is one semiring; confidence *presentation* is a design ethics problem. A UI that paints a 0.6 parse with the same ink as your own words is lying; one that hedges everything is unusable. The rendering language for uncertainty needs invention.

**World-scale Datalog.** Shadow outlines make the EDB grow without bound. Windowing, TTLs on world facts, and demand-driven materialization of foreign regions are all sketched and none proven at the scale of an enthusiastic user's third year.

**Fixpoint UX.** Value-level cycles are errors in v1, and rightly so; but some genuinely useful things (mutual constraint, iterative estimates) want the `#:fix` escape hatch, and the failure modes of user-authored fixpoints inside a notes app are unstudied territory.

**Naming at scale.** Hygiene bridges names and UIDs mechanically, but the human layer — collisions across a decade-old vault, aliases drifting, the difference between "renamed" and "became a different concept" — is ontology maintenance, and no one has made that pleasant yet.

**Schema evolution ergonomics.** Changing a schema against ten thousand conforming-ish blocks is a migration. The compile-lens gives the mechanism (a Put); the workflow — preview, partial application, quarantine of non-conformers — is a product problem the size of a milestone.

**Sharing granularity.** The moment a vault region is shared, block-level permissions, capability delegation across replicas, and "what did the agent see" all arrive at once. Local-first research is actively chewing on this; Arbor should adopt rather than invent.

## Appendix: The Laws

**Law 1.** The document always renders. Failure is a decoration, never a refusal to open.

**Law 2.** The trusted chrome is not programmable by documents.

**Law 3.** Uniform gestures are sacred across all projections.

**Law 4.** The override is the universal fallback Put; divergence is always visible.

**Law 5.** Derived text is always distinguishable from authored text, in every serialization.

**Law 6.** Shadow outlines are pinned: content-addressed, timestamped, re-derived only as an explicit dated act.

**Law 7.** Provenance flows through inference; distrust retracts, visibly.

**Law 8.** The `#lang` line pins semantics; old notes keep their old meanings forever.

**Law 9.** Meaning is owned by the document, execution by the kernel, presentation by no one.

**Law 10.** Identity lives in the sync layer; on block split, the head keeps the UID.

**Law 11.** Never sync the resolved graph; sync source and observations, derive the rest.

**Law 12.** Convergence: identical (source, observations, `#lang` version) implies identical resolved graphs.

**Law 13.** Typing never waits on the kernel.

**Law 14.** The editor survives the kernel.

**Law 15.** Never lose user bytes.

**Law 16.** The clock is a fact; time-dependent recomputation has an explainable input.
